Each time a service's configuration changes, or it is restarted or deployed again, StackBlaze makes a new **release**. Open a service on the canvas and click **Deployment** to see them: **Events, deploys and rollbacks**, newest first.

<Screenshot id="deployments/1-tab" alt="The Deployment tab: the running release titled Redeploy, then earlier ones titled Restarted, Rollback to Add CANVAS_DEMO and Remove CANVAS_DEMO" />

Each row shows:

- the status (see [below](#release-states)), for example **rolling out** while the new version starts, **running** for the one serving now, **superseded** for older ones;
- the image (for example `nginx:1.27`), with its digest when one was recorded;
- when it started, how long the rollout took, and who made it;
- on the right, its title.

## Name a release

When you commit staged changes, the **Commit message** you type becomes the release's title in the history. Here a new variable is committed as **Add CANVAS_DEMO**:

<Screenshot id="deployments/0-commit-message" alt="1 change to apply: Configuration · web, + CANVAS_DEMO, Commit message Add CANVAS_DEMO, Deploy 1 change" />

The message is optional. Without one, the release is titled **Configuration updated**. A service's first release is **First Deploy**.

## Deploy again

**Manual Deploy**, at the top right of the list, offers two actions for a service that runs a Docker image:

- **Deploy latest reference** pulls the image reference again and deploys it, so a tag like `latest` picks up a newer image.
- **Restart service** restarts what is running, with the same configuration.

<Screenshot id="deployments/2-manual-menu" alt="The Manual Deploy menu: Deploy latest reference and Restart service" />

**Restart service** adds a release titled **Restarted**, and **Deploy latest reference** one titled **Redeploy**.

## Services built from git

For a service built from a [git repository](/build-deploy/deploy-from-github), each release row shows the commit it was built from: its short hash and message, for example `92fdae6 Remove build artifacts…`. A release that is still building reads **Deploy building**, with **Cancel**.

**Manual Deploy** offers different actions:

- **Deploy latest commit** builds the newest commit of the branch and deploys it. Ours added a release titled **Manual**; its build **Succeeded** and the new version went live.
- **Deploy a specific commit…** opens **Choose commit to deploy**: "Builds the selected commit from main. Auto-deploy stays on — the next push supersedes this deploy." Pick a commit from the list or paste a SHA, then click **Deploy commit**.

<Screenshot id="deployments/git-1-manual-menu" alt="Manual Deploy for a git service: Deploy latest commit and Deploy a specific commit" />

<Screenshot id="deployments/git-2-commit-dialog" alt="Choose commit to deploy: a search field, two commits with their messages, Cancel and Deploy commit" />

## Actions on a release

Every row has a **⋯** menu:

- **Redeploy** runs the service again. For a Docker image service, it restarts the service with its current configuration, adding a release titled **Restarted**; it doesn't bring back that release's settings. To do that, use **Rollback Config**. For a service built from git, it asks "Redeploy *commit*?" and rebuilds **that release's commit**, not the newest one: "Rebuild and deploy commit … with the exact same configuration."
- **Instant Rollback**, on earlier releases of a service in **Production**. See [below](#instant-rollback).
- **Promote**, on the releases of a preview environment. See [below](#promote-a-preview).
- **Inspect Deployment** opens the service's logs.
- **Copy URL** and **Visit**.
- **Cancel**, only while a release is rolling out. The row also has a **Cancel** button then.

<Screenshot id="deployments/9-row-menu-0" alt="The menu of a release that is rolling out: Cancel, Redeploy, Inspect Deployment, Copy URL, Visit" />

Earlier releases also have **Rollback Config**:

<Screenshot id="deployments/9-row-menu-2" alt="The menu of an earlier release: Rollback Config, Redeploy, Inspect Deployment, Copy URL, Visit" />

**Inspect Deployment** opens the logs over the panel:

## Roll back the configuration

**Rollback Config** puts the service's configuration back to how it was in that release.

<Steps>

<Step>

### Review it

In the release's **⋯** menu, choose **Rollback Config**. The review, titled after the release (here **Rollback to "Remove CANVAS_DEMO"**), lists every setting that will change, from its current value to the one it had then. It says the rollback is "Applied as a new release — add-ons, volumes, and domains stay as they are", and which service will redeploy.

You can type a **Commit message** for the history. Without one, the release is titled after the one you rolled back to.

<Screenshot id="deployments/10-rollback-review" alt="Rollback to Remove CANVAS_DEMO: an optional commit message, Variables CANVAS_DEMO to be removed, and web-tjlc will redeploy" />

</Step>

<Step>

### Roll back

Click **Rollback**. The service redeploys, and a new release appears at the top. Ours, rolling back to **Add CANVAS_DEMO**, brought the `CANVAS_DEMO` variable back and is titled **Rollback to Add CANVAS_DEMO**.

<Screenshot id="deployments/11-after-rollback" alt="The history with the new release Rollback to Add CANVAS_DEMO rolling out above Remove CANVAS_DEMO and Add CANVAS_DEMO" />

</Step>

</Steps>

Rolling back never deletes releases. The ones in between stay in the history, so you can roll forward again the same way.

## Instant Rollback

In the **Production** environment, the **⋯** menu of an earlier release that went live can also have **Instant Rollback**. It puts back that release's image (or code) **and** the variables and settings it ran with, in one step, with no new build. Which of the two an earlier release offers depends on how it was made: on our test service, the first deploy offered **Instant Rollback** and the later image updates offered **Rollback Config**. The release that is running now has neither.

We deployed `nginx:1.26`, then `nginx:1.27`, in **Production**, and rolled back to the first release:

<Steps>

<Step>

### Pick the release

Open the **⋯** menu of the release to go back to and choose **Instant Rollback**.

<Screenshot id="deployments/ir-2-menu" alt="The menu of the First Deploy release: Instant Rollback, Redeploy, Inspect Deployment, Copy URL, Visit" />

</Step>

<Step>

### Confirm

The dialog, here **Roll back to 1.26?**, says what is restored: "Restores this deploy's code and the environment variables and settings it ran with. Add-ons, volumes, domains and your plan stay as they are now." It also warns that **Autodeploy** is turned off, "so new pushes don't undo the rollback". Click **Rollback**, or **Cancel**.

<Screenshot id="deployments/ir-3-confirm" alt="Roll back to 1.26? with Cancel and Rollback" />

</Step>

<Step>

### Check the result

A new release titled **Rollback** rolls out with `nginx:1.26`, and then it's **running**. The releases before it stay in the history.

<Screenshot id="deployments/ir-4-after" alt="The history: Deploy running nginx:1.26 titled Rollback, above the nginx:1.27 release and the First Deploy" />

</Step>

</Steps>

After the rollback our service had **Autodeploy** off. For a service built from git, turn it back on in **Settings** → **Deploy** once the fix is pushed; until then, pushes are listed as skipped and nothing deploys.

<Callout type="warn">
No rollback touches your data. A database migration that ran with a newer release stays in place when you roll the code back. Write migrations so the release before them still works with the new schema (add columns and tables; drop them in a later release).
</Callout>

## Promote a preview

In a [preview environment](/build-deploy/preview-environments), a release's **⋯** menu has **Promote**. It asks "Promote to production?" and rebuilds the service the preview was copied from (in the environment it came from) from the preview's commit. The service's address stays the same. For a Docker image service, the source service is rolled onto the preview's image tag instead.

## Release states

A release's status reads, from start to finish:

| Status | Meaning |
| --- | --- |
| **queued** | Accepted, waiting to start. |
| **building** | The image is being built. |
| **running pre-deploy** | The [pre-deploy command](/configure/start-and-build#pre-deploy) runs in the new image. |
| **rolling out** | The new version is starting; the old one still serves. |
| **running** | This release is serving now. |
| **superseded** | It went live, then a newer release took over. |
| **failed** | The build, the pre-deploy command or the rollout failed. The release before it keeps serving. |
| **canceled** | Canceled, or replaced by a newer deploy before it went live. |

Events that aren't deploys are listed too, such as **Skipped** (a push that didn't deploy, see [Which pushes build](/how-it-works#which-pushes-build)), **Crashed**, **Out of memory**, **Paused** and **Resumed**.

## From the CLI

```sh
stackblaze deployments list -p my-shop -e production -a web
```

lists the releases with their ID, status (`live`, `superseded`, `rolling_out` …), trigger, image or commit, and message.

```sh
stackblaze deployments rollback <id> -p my-shop -e production -a web --wait
```

rolls back to a release in full, like **Instant Rollback**: image and configuration, with auto-deploy turned off. Without an ID it picks the previous successful release. `--image-only` puts back only the image and keeps today's configuration and auto-deploy; `-y` skips the question.

## From the API

All of these need an [API token](/security/api-tokens) allowed to change the service:

| Call | What it does |
| --- | --- |
| `GET /api/deployments/{project}/{environment}/{service}` | The release history. |
| `POST /api/deployments/build/{project}/{environment}/{service}` | Build and deploy, optionally a given `commitSha`. |
| `POST /api/deployments/rollback-deploy/{project}/{environment}/{service}/{id}` | Instant Rollback to a release. |
| `GET /api/deployments/rollback/{project}/{environment}/{service}/{revision}` | Preview a Rollback Config: the current and earlier configuration. |
| `POST /api/deployments/rollback/{project}/{environment}/{service}/{revision}` | Apply the Rollback Config, with an optional `message`. |
| `POST /api/deployments/promote/{project}/{environment}/{service}` | Promote a preview's service. |
