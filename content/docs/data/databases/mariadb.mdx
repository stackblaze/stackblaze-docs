MariaDB is a MySQL-compatible relational database. Like every database, it belongs to one environment, and any app in that environment can connect to it.

<Steps>

<Step>

### Add MariaDB

On the project canvas, click **+ Service**, then **Database or cache**, and pick **MariaDB**. A card appears under **Databases** marked **Ready to deploy**.

<Screenshot id="mariadb/1-ready" alt="The MariaDB card on the canvas, Ready to deploy" />

</Step>

<Step>

### Deploy it

Click the card, then **Deploy** (or **Remove from canvas** to drop it). It deploys with the catalog defaults: MariaDB 11.4, a 1 GiB volume and the database `app`.

<Screenshot id="mariadb/2-review" alt="MariaDB review: Ready to deploy, with Remove from canvas and Deploy" />

<Screenshot id="mariadb/3-running" alt="The MariaDB card, Running" />

</Step>

<Step>

### Connect an app

Click **MariaDB** on the card, open **Settings**, and in **Connections** turn on the switch next to your app. Then **Commit 1 change** and **Deploy 1 change**. The app redeploys.

<Screenshot id="mariadb/6-connect" alt="Connections with nginx switched on, marked staged" />

Connecting added these variables to the app:

| Variable | |
|---|---|
| `MYSQL_HOST`, `MYSQL_PORT` | the in-cluster address and port (`3306`) |
| `MYSQL_USER`, `MYSQL_DATABASE` | the user (`root`) and database (`app`) |
| `MYSQL_PASSWORD` | read from the database's secret ("Provided by add-on") |

<Screenshot id="mariadb/7-variables" alt="The app's variables with MYSQL_HOST to MYSQL_DATABASE" />

Connecting also adds `DATABASE_URL`, a `mysql://` URL built from the `MYSQL_*` values. A variable you set yourself with the same name always wins. If another connected database already sets `DATABASE_URL`, this one's variables are also added under its own prefix, such as `MARIADB_DATABASE_URL`.

From the connected app, the `MYSQL_*` values reached the database:

```text
$ MYSQL_PWD="$MYSQL_PASSWORD" mariadb -h "$MYSQL_HOST" -P "$MYSQL_PORT" -u "$MYSQL_USER" "$MYSQL_DATABASE" -e "select version();"
11.4.13-MariaDB-ubu2404-log
```

</Step>

</Steps>

## Connection details

**Settings** → **Access** → **Connect from apps** shows the **Host**, the short **Service** name, **Username**, **Password** and **Database**. **Connection URL** gives a `mysql://` URL and a JDBC URL; **Environment snippet** gives `DATABASE_URL` and the `MYSQL_*` lines. These work from apps in the same environment and are "not reachable from the public internet".

<Screenshot id="mariadb/5-access" alt="Access: Host, Service, Username, Password, Database, Connection URL and Environment snippet" />

## Connect from your machine

`stackblaze connect mysql` opens a MariaDB shell through a connected app, without opening the database to the internet. `--local` runs your own `mysql` client through a private tunnel; `--tunnel` keeps a local port open for GUI tools. They work like [PostgreSQL's](/data/databases/postgresql#connect-from-your-machine).

```sh
stackblaze connect mysql --local -p shop -e dev -a web
```

## Server settings

On our database:

```text
> SHOW VARIABLES WHERE Variable_name IN ('character_set_server','collation_server','binlog_format','log_bin');
binlog_format         ROW
character_set_server  latin1
collation_server      latin1_swedish_ci
log_bin               ON
```

- The server's default character set is `latin1`. For full Unicode (including emoji), create your databases and tables with `CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci`, or set it in your app's connection.
- Binary logging is on, in `ROW` format with full row images. A change-data-capture connector, such as the [Kafka](/addons/kafka) MySQL / MariaDB connector, works without extra setup.

## Connection pooling

To pool connections or split reads and writes in front of MariaDB, add [ProxySQL](/addons/proxysql).

## Import a dump

MariaDB dumps load from your machine with `stackblaze addons import dump.sql --local`. See [Import a database dump](/data/databases/import-dump#import-a-mariadb-dump).

## SQL console

The database address on the MariaDB card (`db.…`) opens a SQL console in a new tab. You're signed in, and the database is listed under **Shared**.

<Screenshot id="mariadb/console" alt="The SQL console with the project's MariaDB under Shared" />

Open a SQL editor, type a query and run it with **Ctrl+Enter**. Here `SELECT VERSION() AS version, DATABASE() AS db;` returned the MariaDB version and the database name, `app`.

<Screenshot id="mariadb/console-query" alt="A query in the SQL editor and its result: the MariaDB version and the database app" />

The [Database console](/data/console) page covers the rest: the navigator, scripts, the execution plan, editing rows and exporting results.

## Connect from outside StackBlaze

**Public access** opens the database to clients outside the platform, only from the IP addresses you allow, and only over TLS. Enter your addresses in **Allowed IPs** (CIDR ranges work too) and turn the switch on. You get an **Address** and a **Connection string**.

<Screenshot id="mariadb/19-public-on" alt="Public access, On, with Address, Connection string and Allowed IPs" />

We connected from an allowed address with a MySQL client over TLS. The address took a few minutes after the switch turned on before it accepted connections. After we turned it off, it no longer accepted them. Turning it off asks first: "Turn off public access? Clients outside the platform will be disconnected."

## High availability

High availability works differently for MariaDB than for PostgreSQL or Valkey: it builds a **new** cluster. **Settings** → **HA** → **Enable HA** asks first:

> Builds a new 3-node Galera cluster from a fresh backup, then cuts your apps over to it. This instance stays for rollback. You will be taken to the new cluster when promotion finishes — HA cannot be toggled back off.

<Screenshot id="mariadb/13-ha-off" alt="High availability: Single primary, with Enable HA" />

<Screenshot id="mariadb/14-ha-confirm" alt="Enable high availability? Builds a new 3-node Galera cluster" />

While it runs, the section lists its steps: **Preflight checks**, **Fresh backup**, **Provision HA cluster**, **Wait for cluster ready**, **Cut over apps**, **Verify & finalize**. Ours finished **Healthy** with **3/3** ready (one primary, two replicas), and our connected app was moved to the new cluster.

<Screenshot id="mariadb/15-ha-on" alt="High availability: 3 instances, Galera, Healthy, 3/3 ready" />

The canvas then shows two MariaDB cards. The original says it was "Promoted to …" and "is retained for rollback", with **Open HA cluster**.

<Screenshot id="mariadb/16-rollback" alt="The original instance: promoted to the HA cluster, retained for rollback, Open HA cluster" />

## Deployments, logs and metrics

**Deployment** lists deploys and restarts, and **Logs** streams the database's output (see [PostgreSQL](/data/databases/postgresql#deployments) for their menus).

<Screenshot id="mariadb/8-deployment" alt="MariaDB: the Deployment tab" />

<Screenshot id="mariadb/9-logs" alt="MariaDB: the Logs tab" />

**Metrics** shows the last **2h**, **24h** or **7d**, with **Refresh**. At the top: **Connections** (open sessions), **Cache hit** (buffer pool hits), **Threads** (actively running) and **Queries** (statement rate). Below that are charts for **Host resources** (Memory usage, CPU usage), **Workload** (Threads running, Queries / s, Commits / s, Rollbacks / s), **Health** (Buffer pool hit, Slow queries / s) and **Network** (Bytes sent / s, Bytes received / s).

<Screenshot id="mariadb/10-metrics" alt="MariaDB: the Metrics tab" />

## Backups

A recovery point holds a dump of each MariaDB database. Restore it as a copy like any database: see [Backups and restore](/data/databases/backups). MariaDB has no point-in-time recovery.

## Delete

**Delete add-on** at the bottom of **Settings** deletes the database and its data. Disconnect its apps first.
