A database is added to one environment of a project, and any app in that environment can connect to it. This guide adds PostgreSQL to the **Dev** environment and connects an app that is already running there.

<Steps>

<Step>

### Add PostgreSQL

On the project canvas, click **+ Service**, then **Database or cache**. Pick **PostgreSQL**.

<Screenshot id="postgresql/1-databases" alt="The Databases list in the add menu, with PostgreSQL" />

The list also has **[TimescaleDB](/data/databases/timescaledb)**: PostgreSQL on a TimescaleDB image, for time-series data, with the `timescaledb` extension already created in the `app` database. It is the open-source edition ("no compression or continuous aggregates"). It's a separate choice when you add the database: an existing database can't be switched to or from it.

<Screenshot id="data/databases-menu" alt="PostgreSQL, TimescaleDB and Valkey in the database list" />

A PostgreSQL card appears under **Databases** marked **Ready to deploy**. Nothing has been created yet.

<Screenshot id="postgresql/2-ready" alt="The PostgreSQL card on the canvas, Ready to deploy" />

</Step>

<Step>

### Review and deploy

Click the card. The catalog defaults are PostgreSQL 17, one instance, a 1 GiB volume, the user `postgres` and the database `app`. The panel says the database "deploys with the catalog defaults", and that size, high availability and connections are tuned in this panel once it is running. Click **Deploy**.

<Screenshot id="postgresql/3-review" alt="Ready to deploy, creates it on Dev right away, with Remove from canvas and Deploy" />

If you change your mind, **Remove from canvas** takes the card away without creating anything.

When it is ready, the card shows **Running**.

<Screenshot id="postgresql/4-running" alt="The PostgreSQL card, Running" />

</Step>

<Step>

### Find the connection details

Click **PostgreSQL** on the card, open **Settings**, and look under **Access**:

- **Connect from apps**: the **Host**, the short **Service** name, **Username**, **Password** and **Database**. The port is `5432`.
- **Connection URL**: the same details as a `postgresql://` URL, plus a **JDBC** URL. These work from apps in this environment and are "not reachable from the public internet".
- **Environment snippet**: ready-made lines (`DATABASE_URL`, `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, …) to paste into an app's variables.

<Screenshot id="postgresql/5-access" alt="Access: Connect from apps, Connection URL and Environment snippet" />

</Step>

<Step>

### Connect an app

Further down, **Connections** lists the apps in the environment. Turn on the switch next to your app. The change is staged.

<Screenshot id="postgresql/6-connect" alt="Connections with nginx switched on, marked staged" />

Close the panel, click **Commit 1 change**, then **Deploy 1 change**. The app redeploys.

<Screenshot id="postgresql/7-commit" alt="1 change to apply: nginx ⇄ postgresql, off → on" />

</Step>

<Step>

### Check the app's variables

Open the app and go to **Variables**. Connecting added:

| Variable | |
|---|---|
| `PGHOST`, `PGPORT` | the database's in-cluster address (the primary) |
| `PGHOST_RO`, `PGPORT_RO` | the read-only address of the replicas, which only has instances behind it once [high availability](#high-availability) is on |
| `PGUSER`, `PGDATABASE` | the user and database name |
| `PGPASSWORD` | read from the database's secret ("Provided by add-on") |

<Screenshot id="postgresql/8-variables" alt="The app's variables, with PGHOST to PGDATABASE and PGPASSWORD provided by add-on" />

</Step>

</Steps>

Connecting also adds `DATABASE_URL`, a `postgres://` URL built from the `PG*` values. A variable you set yourself with the same name always wins.

When the database includes its own connection pooler (some templates add one), connecting also adds `PGHOST_POOLER` and `PGPORT_POOLER`, the pooler's address.

Build steps and the **Pre-deploy** command get the same variables. When the service has no usable `DATABASE_URL` of its own, they get one built from the `PG*` values, so a migration that reads `DATABASE_URL` works at build time too.

If the app is connected to two databases that both set `DATABASE_URL` (for example PostgreSQL and MariaDB), the first keeps the plain names and the second also gets its whole set under its own prefix, such as `MARIADB_DATABASE_URL` and `MARIADB_MYSQL_HOST`.

From the connected app, `psql "$DATABASE_URL"` reached the database:

```text
$ psql "$DATABASE_URL" -At -c "show server_version;" -c "select current_database();"
17.5 (Debian 17.5-1.pgdg110+1)
app
```

To disconnect, turn the switch off and deploy the change; the `PG*` variables are removed from the app.

## Connect from your machine

`stackblaze connect postgres` opens a `psql` shell on the database without opening it to the internet. Name the app it's connected to:

```sh
stackblaze connect postgres -p shop -e dev -a web            # psql runs inside the app
stackblaze connect postgres --local -p shop -e dev -a web    # psql runs on your machine
stackblaze connect postgres --tunnel -p shop -e dev -a web   # keep a local port open for GUI tools
```

- By default `psql` runs inside the app's instance.
- `--local` runs your own `psql` through a private tunnel: `Tunnel 127.0.0.1:33567 → postgres addon "postgresql-u0kr". Running local psql…`
- `--tunnel` keeps the tunnel open and prints the host, port, user and database for a GUI tool. `--print-only` prints a `postgresql://…@127.0.0.1:<port>/…` connection string instead of starting a client, and `--port` picks the local port.

The tunnel listens on `127.0.0.1` only, closes after 30 minutes idle, and needs write access to the app. When the app has several databases, add `--instance <name>`.

## Connect from outside StackBlaze [#public-access]

By default the database is only reachable from apps in the same environment. **Public access** opens it to clients outside the platform (a laptop, a BI tool, another cloud), only from IP addresses you allow, and only over TLS.

<Steps>

<Step>

### Allow your IP addresses

Open the database's **Settings** → **Access** and find **Public access**. In **Allowed IPs**, enter the addresses that may connect, separated by commas. Ranges in CIDR form (like `198.51.100.0/24`) work too.

**Allow any IP** lets anyone who has the password connect. The panel marks it "not recommended".

<Screenshot id="postgresql/m-public-off" alt="Public access, Off, with an allowed IP entered" />

</Step>

<Step>

### Turn it on

Turn on the **Public access** switch. You get an **Address** and a **Connection string** that ends in `?sslmode=require`.

<Screenshot id="postgresql/m-public-on" alt="Public access, On, with Address, Connection string and Allowed IPs" />

</Step>

<Step>

### Connect

Copy the **Connection string** and use it from an allowed address, for example:

```sh
psql "postgresql://postgres:<password>@<address>/app?sslmode=require"
```

When we did this, the address refused connections for a short while after the switch turned on, then accepted them.

</Step>

</Steps>

To change the list later, edit **Allowed IPs** and click **Save allowed IPs**. Turning the switch off asks "Turn off public access? Clients outside the platform will be disconnected." After that, the address no longer accepts connections.

**Settings** → **Extensions** lists the PostgreSQL extensions available on the database's image and how many are enabled. Extensions are per database: pick the database (for example `app`) in the menu next to **Refresh**. Use **Filter by name…** to find one, then turn its switch on.

<Screenshot id="postgresql/m-ext-on" alt="Extensions, filtered to pg_trgm, switched On" />

## High availability

A new database runs as a **Single primary**. **Settings** → **HA** → **Enable HA** turns it into a cluster of three.

<Screenshot id="postgresql/m-ha-off" alt="High availability: Single primary, with Enable HA" />

The dialog says it "Scales the Postgres cluster to 3 instances. This is a one-way upgrade — there is no in-place downgrade to a single primary." Click **Enable HA**.

<Screenshot id="postgresql/m-ha-confirm" alt="Enable high availability? with Cancel and Enable HA" />

When it is done, the section shows the cluster: its health, **3/3** replicas ready, which instance is the primary, the mode (**Streaming replication**), and each member with its role (one **primary**, two **replica**).

<Screenshot id="postgresql/m-ha-on" alt="High availability: 3 instances, Healthy, one primary and two replicas" />

Connected apps keep the same variables: `PGHOST` still points at the primary, and `PGHOST_RO` now reaches the two replicas, so you can send read-only queries there.

The **Logs** tab streams the database's logs.

## Import a dump

To load an existing database, see [Import a database dump](/data/databases/import-dump).

## Backups

Back up the database, restore it as a copy, and move your apps onto the copy with **Switch instance**: see [Backups and restore](/data/databases/backups). A recovery point holds a dump of the database.

PostgreSQL also has [point-in-time recovery](/data/databases/backups#point-in-time-recovery), through the API only.

## Delete

**Delete add-on**, at the bottom of **Settings**, deletes the database and its data. It is only available once no apps are connected: disconnect them first in **Connections**.
