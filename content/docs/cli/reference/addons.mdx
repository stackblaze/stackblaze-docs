## addons backups

```text
Usage: stackblaze addons backups|backup [options] [command]

Dumps of one PostgreSQL / MariaDB database (never creates a schedule);
whole-environment backups: `stackblaze backups`

Options:
  -h, --help                 Print help

Commands:
  list [options] [addon]     List dumps and running dump/restore jobs of a
                             database
  status [options] [addon]   Show whether the environment's scheduled backups
                             cover a database
  create [options] [addon]   Dump a database now (no schedule needed)
  restore [options] [addon]  Restore a dump as a NEW database (`<db>-restored`,
                             billed like any database); the existing database
                             is never touched
  help [command]             Print this message or the help of the given
                             subcommand(s)

<addon> is the add-on's instance name (or its type, e.g. postgres, when the
app has one of that type); default the app's only database add-on.

PostgreSQL and MariaDB databases are backed up as dumps: `status` shows
whether the environment's scheduled backups cover it, `create` takes a
dump now (no schedule needed), and `restore` creates a NEW database from a
dump (--backup <name>, default the newest). The existing database is never
touched: connect your app to the new one when you are ready, and delete the
old one yourself. Both are billed until then.

The new database is named `<database>-restored` and made from the dump
itself, also when the source database is gone. (Older servers can only
restore a dump that a recovery point holds; `list` shows which dumps have
one.) Valkey has no dumps. These commands never turn on scheduled backups.

Examples:
  $ stackblaze addons backups status web-postgresql
  $ stackblaze addons backups create --wait
  $ stackblaze addons backups restore web-postgresql --backup <name> --wait
```

## addons import

```text
Usage: stackblaze addons import [options] <source> [addon]

Load a dump (pg_dump plain SQL or -Fc archive) into a PostgreSQL add-on, inside
the cluster: from a local file, an http(s) URL or a Storage bucket add-on

Options:
  --api-url <url>        StackBlaze API base URL (env STACKBLAZE_API_URL)
  --token <token>        API token, sb_pat_... (env STACKBLAZE_TOKEN)
  -p, --project <name>   Project name
  -e, --env <name>       Environment name (default: production)
  -a, --app <name>       App name
  --json                 Output JSON (same as -o json) (default: false)
  --addon <name>         Database add-on (instance or name); same as the
                         [addon] argument
  --instance <name>      Addon instance when multiple match
  --jobs <n>             Parallel pg_restore workers for an archive (1-8,
                         default 2)
  --wait                 Follow the import to its end and print the result
                         (default: false)
  --timeout <seconds>    Max --wait time; the import carries on after it (0 =
                         no limit) (default: "21600")
  --local                Run psql / pg_restore / mysql on this machine through
                         a private tunnel instead (also MariaDB, -Fd
                         directories) (default: false)
  --clean                With --local, PostgreSQL archives: drop the objects
                         the dump recreates first (default: false)
  --stop-on-error        With --local: stop at the first error instead of
                         carrying on (default: false)
  -y, --yes              Skip confirmation prompt (default: false)
  -o, --output <format>  Output format: text or json (choices: "text", "json")
  -h, --help             Print help

<source> is one of:
  ./dump.sql | ./db.dump        a local file: uploaded once (up to 5 GB), then loaded in the cluster
  https://…                     a URL the cluster downloads (a presigned S3 URL works)
  s3://<bucket>/<key>           an object of a Storage bucket add-on of the environment
                                (<bucket> is the add-on's name; no other S3 buckets)

The dump is checked before anything is written: an archive (pg_dump -Fc,
also gzipped) must list cleanly, plain SQL must contain its
"-- PostgreSQL database dump complete" line. The database's disk must have
about 3x the dump's size free, or the import is refused ("Increase its
storage first"). Archives load with pg_restore -j N --no-owner
--no-privileges, plain SQL with psql ON_ERROR_STOP; both stop at the first
error. The dump goes INTO the add-on's existing database: use an empty one.
Use the same or an older PostgreSQL version's pg_dump than the add-on runs.
A plain SQL dump is run as it is: make it with `pg_dump --no-owner --no-acl`.

--local is the previous behaviour: the client runs on this machine against
the same private tunnel as `stackblaze connect --local` (MariaDB / MySQL
dumps and pg_dump -Fd directories need it).

Examples:
  $ stackblaze addons import backup.dump --addon postgres -p shop --wait
  $ stackblaze addons import "https://example.com/dump.sql.gz?sig=…" postgres -p shop --wait
  $ stackblaze addons import s3://files/dumps/db.dump --addon postgres -p shop --wait
  $ stackblaze addons import dump.sql --local -a web
```

## addons export

```text
Usage: stackblaze addons export [options] [addon]

pg_dump -Fc a PostgreSQL add-on to a Storage bucket add-on of the environment,
inside the cluster

Options:
  --api-url <url>        StackBlaze API base URL (env STACKBLAZE_API_URL)
  --token <token>        API token, sb_pat_... (env STACKBLAZE_TOKEN)
  -p, --project <name>   Project name
  -e, --env <name>       Environment name (default: production)
  -a, --app <name>       App name
  --json                 Output JSON (same as -o json) (default: false)
  --to <s3-uri>          Where the dump goes: s3://<bucket>/<key>, <bucket> a
                         Storage bucket add-on of the environment
  --addon <name>         Database add-on (instance or name); same as the
                         [addon] argument
  --instance <name>      Addon instance when multiple match
  --wait                 Follow the export to its end (default: false)
  --timeout <seconds>    Max --wait time; the export carries on after it (0 =
                         no limit) (default: "21600")
  -o, --output <format>  Output format: text or json (choices: "text", "json")
  -h, --help             Print help

<bucket> is the name of a Storage bucket add-on of the same environment;
other S3 buckets are not supported. The dump is a pg_dump custom-format
archive of the add-on's database, checked (pg_restore -l) before it is
uploaded; `addons import s3://…` loads it into another add-on. Counts as a database dump for your plan.

Examples:
  $ stackblaze addons export postgres -p shop --to s3://files/dumps/shop.dump --wait
```

## addons expose

```text
Usage: stackblaze addons expose [options] [addon]

Make an add-on reachable from outside: databases via the edge (IP allow-list),
S3/ClickHouse/RabbitMQ via HTTPS

Options:
  --api-url <url>        StackBlaze API base URL (env STACKBLAZE_API_URL)
  --token <token>        API token, sb_pat_... (env STACKBLAZE_TOKEN)
  -p, --project <name>   Project name
  -e, --env <name>       Environment name (default: production)
  -a, --app <name>       App name
  --json                 Output JSON (same as -o json) (default: false)
  --allow <ip/cidr>      Address allowed to connect (repeatable, or
                         comma-separated)
  --allow-all            Allow any address (only the database password protects
                         it) (default: false)
  -y, --yes              Skip the --allow-all confirmation (default: false)
  -o, --output <format>  Output format: text or json (choices: "text", "json")
  -h, --help             Print help

Re-run with a different --allow list to change who may connect. The server
decides which engines can be exposed and says why when it cannot (exit 3).
Credentials: `stackblaze addons info <addon> --reveal`.
```
